Package 0.5.3 changes release publishing, not squadron scheduling behavior. Maintainers now publish through a single manual **Actions → Publish release** workflow by entering the version number. The workflow validates the current default-branch commit, builds and checks the Word packages twice, generates the release notes, creates or resumes a matching draft release, uploads and verifies every asset, and only then publishes the release. This sequence is compatible with GitHub immutable releases and prevents a published release from appearing without its operator downloads.

A failed run before draft creation leaves no release. A failed run after draft creation leaves a mutable draft that can be safely resumed by rerunning the same version; existing draft assets are byte-checked before missing files are uploaded. The workflow never repairs or replaces an already-published immutable release and never moves an existing tag.

There are no scheduling-policy, authority, operator-guide, Local Guidance, or weekly-folder changes in 0.5.3. Existing installations do not need to update solely because of this maintainer automation change. If an installation adopts the 0.5.3 System package for version consistency, use the normal next-week update process and preserve Local Guidance and weekly work.
